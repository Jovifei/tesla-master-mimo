# ADR提案：用户本地详细档案 + 云端轻量索引 + 可选完整冷归档

日期：2026-10-02。
状态：**PROPOSED，尚未实施迁移或删除策略**。
关联：`RPT-2026-10-02-history-memory-repair.md`、`ARCH-DECISION-2026-09-27-fleet-teslamate-hybrid.md`、`TESLAMATE-ARCHIVE-BRIDGE.md`。

## 1. 背景与不变约束

用户希望大量详细数据保存在用户本地，少量精要/重要数据保存在运营云端。这个方向可以降低日常服务器读取、传输和热存储负担，但不能靠删除数据解决错误读取，也不能仅凭手机在线一次就删除唯一完整档案。

2026-09-27权威架构仍是：多用户由Fleet OAuth/车辆钥匙/Fleet Telemetry采集；Jovi已有TeslaMate通过个人只读归档桥接迁移。不得将个人TeslaMate改成多人共享采集器。此前“云端永不存历史”已经不是当前约束；本提案也不重新启用旧两日自动删除。

本次故障的第一原因类别是无界加载放大，而非已证明原始记录太多或重复。查询优化必须先部署验证；存储迁移是独立第二阶段。

## 2. 建议的分层

```text
真实车辆 → Fleet Telemetry接收与可信归属 → 有界事件缓冲/追加点
                                               ↓
                                    会话摘要与来源/质量/版本
                                               ↓
                             JourVolt PostgreSQL（热数据）
                           ↙                         ↘
                App本地详细档案                 完整冷归档（可选）
            Room索引 + 分块压缩文件             私有对象存储/用户备份
                           ↘                         ↙
                             按需下载/校验/换机恢复

微信小程序：读取同一服务的摘要、近期按需详情和轻量缓存；不是唯一长期档案。
```

| 层 | 保存内容 | 默认访问方式 |
| --- | --- | --- |
| 云端热数据 | canonical用户/车辆、来源映射、授权状态、行程/充电摘要、计量口径、质量/覆盖率、首尾观测、版本、归档清单、校验值、设备同步水位 | 查询只取需要的列；有界分页，不触碰全量原始点 |
| 云端近期详细数据 | 未结束行程、未封装归档、尚未确认持久化的近期事件/点 | 追加、有界分块；不在元数据查询解码 |
| 原生App本地 | 用户选择或自动下载的完整行程路线、充电采样、完整性清单、摘要索引 | 默认本地优先；无数据按需下载，不整年加载进内存 |
| 小程序本地 | 摘要、分页游标、近期选中详情的有限缓存 | 限额/LRU/明确缓存失败与离线状态；不得当唯一备份 |
| 冷归档 | 完整原始数据的分块压缩副本及manifest | 私有读取授权、流式传输、短期下载能力、断点恢复；无全桶公开链接 |

## 3. 必须明确的产品选择

A. **只在本地保存完整原始点，云端仅留摘要。** 可以这样做，但旧手机损坏、卸载、文件丢失或未做个人备份后，原始路线不可恢复；新手机只能恢复摘要及云端仍在窗口内的详情。需要用户明确接受，界面显示“完整路线仅存本机/未备份”。

B. **本地完整副本 + 云端轻量热库 + 完整冷归档。** 更适合保留现有换机恢复承诺；运营云端仍有完整归档，但不是把全部点常驻PostgreSQL热查询/Go内存。压缩、存储费用、保留期应实测评估，不能在没有账户和负载数据时编造成本数字。

建议优先B，先让热库与API轻量化；A作为明确告知的用户选择。当前没有用户确认具体保留期限，不能直接设置“48小时后删除”。

## 4. 数据结构建议（新增设计，不是现有接口）

稳定归档身份应包含：`owner_user_id + stable_vehicle_id + source_instance_id + source_vehicle_id + source_kind + source_record_id`。canonical session/public ID与来源身份分离，变更 public ID 不改变原始档案归属。

建议manifest字段：

- schema_version、archive_id、canonical_session_id、source、quality_state、time_range。
- 每块的chunk_index、sample_count、compressed_size、uncompressed_size、SHA-256、编码/压缩版本。
- summary_revision、detail_revision、complete标志、明确的缺失范围、端点坐标系。
- 存储位置/归档状态仅由服务端管理，客户端不自行指定其他租户对象键。

原始观测必须保留null与零、source、质量、时间、单位；不将充电功率用作驾驶功率。地图简化路线是派生展示资产，应带原始版本、简化参数、点数和derived标识；完整导出仍保留原始点。

建议详情接口按chunk/cursor返回明确next_cursor、完整性和总点数。任何点数限制都必须显式返回分块信息，不能静默截断后标记complete。旧客户端依赖完整详情，应通过接口版本协商兼容，而不是无提示改成只有首尾点。

## 5. 可靠同步与本地ACK

下载流程：请求manifest → 校验授权 → 逐块下载到临时文件 → 限制解压长度 → 校验SHA/点数/版本 → 原子落盘 → 更新本地事务索引 → 回读验证 → 上报设备确认水位。

ACK至少绑定account、stableVehicle、device、archive、revision和hash；不能用“HTTP200”“页面显示了摘要”“统计聚合完成”替代完整详情已持久化。

一个设备ACK不代表所有设备收到，更不代表未来的新手机能够恢复。设备丢失/撤销、离线设备、旧revision、撤销授权和删除请求都应有独立规则。远端空页是暂时没有数据，不是删除指令；明确删除需要服务端revision/tombstone。

当前Android SyncRepository读取详情后写摘要与聚合，不足以证明完整原始positions已经持久保存；TripRouteCache等现有缓存须逐路径审计，不应由名字推断完整备份能力。

## 6. 保留与迁移：先双写校验，后考虑清理

第一步：纯查询止血，本轮已提供，历史零删除。
第二步：独立摘要列、样本数和版本清单；逐批回填、检验来源和计数，保留旧JSON读取回退。
第三步：完整块写入私有归档；校验hash/数量/完整解码；断电、重复导入和中断恢复通过。
第四步：App本地档案与小程序有界缓存，完成离线与换机回归。
第五步：明确保留政策后才讨论热库清理。完整归档副本已可恢复、清单一致、备份可用、租户授权正确且达到保留条件时，才逐批移除热详细payload；先dry-run清单，保留宽限与回滚。摘要/索引/原始来源不得错误清除。

以下条件不允许删除：仅收到客户端ACK、仅上传成功但未校验、对象存在但无法解密、完整数据只剩一份临时缓存、归档版本不匹配、用户未同意新保留策略。

## 7. 容量、并发与费用预算

API热请求应与归档/大详情的并发预算分离；采用全局上限+租户公平上限，队列有界且可取消，忙时返回明确可重试状态，不能悄悄丢数据。先测不同点数、会话数和并发数下的Go分配、峰值RSS、数据库CPU/IO与p95/p99，再设置预算。

GOMEMLIMIT是Go软限制，不是容器硬上限，也不能回收仍被请求引用的大对象。应给数据库、MQTT、反向代理、操作系统和非Go内存留出余量；不可把所有容器上限总和设置到宿主可用内存以上后期待GC解决。

实时写入下一步采用固定大小会话状态 + 追加点/块：当前每次事件整段读改写会随行程增长产生写放大。须保持按用户/车辆/来源去重、跨重启幂等、红灯不切行程、充电能量基线和完成事件唯一性。

## 8. 隐私与账号边界

云端摘要也包含敏感行程信息，不因数据量少就免除保护。令牌/绑定凭据仅服务端加密保存；文件本地加密采用平台密钥管理，不硬编码通用密钥。日志、指标和对象路径不得包含明文VIN、token、精确私人地址或原始轨迹。对象读取每次核验租户，不向陌生新用户恢复旧车主历史。

换机恢复、退出登录、解除绑定、撤销Tesla授权、删除账号、本地清除和云端删除是不同操作，应独立说明。更改存储事实后同步更新隐私文档和告知，不把技术提案当成已审核的正式法律文本。

## 9. 验收标准

在同一源码/配置下，用多种点数和至少两账号相同数字carId验证：元数据内存不随全部路线点增长；大详情不会饿死登录；索引分页正确；完整归档point_count/hash逐项一致；网络中断/重启可续传；空远端不删本地；旧/新设备和小程序均不串号；明确丢失风险或完整换机恢复可证明。

本提案未指定用户数容量、成本或上线日期，均需真实压测与产品决策。

## 技术依据（外部资料，与项目事实分开）

- Go GC guide：`https://go.dev/doc/gc-guide`，软内存限制与live heap、thrashing边界。
- PostgreSQL TOAST：`https://www.postgresql.org/docs/current/storage-toast.html`，压缩/离线存储和按列访问。
- PostgreSQL aggregates：`https://www.postgresql.org/docs/current/functions-aggregate.html`，COUNT仍需按可见行执行。
- Taro微信存储API：`https://docs.taro.zone/docs/apis/storage/batchSetStorageSync`，KV单key和总容量及缓存边界；不能把该限制推广为所有文件系统API上限。
