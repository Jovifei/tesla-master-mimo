## 为什么出现 63 万个点

源归档清单：413 条行程、632055 个路线点，单条最大 29583 个点；另有 53 条充电记录。路线 JSON 的数据库存储量约 9.13 MB，该存储量不等于展开后的运行内存。

路线点用于描述行程中不同时间的位置及观测值。平均每条约 1530 个点不能单独证明异常，也不能推出实际采样周期。尚未完成重复导入和采样频率审计，不把数量直接判定为伪造或重复。

## 源码已确认的高风险读取

图谱 Go 定位不足，以下通过当前 main 源码定向核验：

| 文件/函数 | 实际需求 | 当前问题 |
| --- | --- | --- |
| deploy/jourvolt-dev-mock/main.go：vehicleItems | 行程/充电数量 | 两次 history 读取完整历史后 len |
| deploy/jourvolt-dev-mock/readiness.go：historyReadinessSource | 来源分类 | history 读取完整历史后遍历来源 |
| deploy/jourvolt-dev-mock/telemetry_service.go：hasHistory | 是否存在历史 | history 读取完整历史后判断 len |

完整历史读取会解码 route_json/charge_points_json，并构造响应对象；归档路线还可能存在原始点和转换点的中间副本。大历史、多次状态查询和并发请求会叠加内存。OOM 已证实；这些读取是明确风险，尚未用分配剖析把每次 OOM 精确归因到某个请求。

当前已有 historySummaries 生产数据库摘要路径，历史列表已采用摘要，详情具备单会话读取；遗漏的是计数、存在性、来源等元数据路径。

## 修复顺序与验收

1. 最小止损：元数据读取复用摘要路径，保持来源、数量、隔离、空值语义；后续使用 COUNT/EXISTS/必要字段查询，避免连全部摘要也无界读取。
2. 历史列表分页；详情只读当前会话。大路线展示可简化或分块，但完整归档必须保留，不静默删点。
3. 限制大详情/归档并发、查询超时、资源预算，并监控内存、容器重启、502。扩容不能替代读取优化。
4. 隔离 PostgreSQL 大路线回归：元数据返回正确，内存分配不随路线点数量线性增长；多账号并发、拒绝跨用户读取；完整详情仍能恢复真实路线。
5. 测试通过后提交、同步 main，备份并仅替换 API，保留回退版本。核验实际 build_sha、登录入口、内存趋势及重启次数；禁止仅凭 /healthz 宣称修复。
6. 若涉及 Android 变更，按既定门禁测试、签名构建、同签名 install -r 真机验证，保留登录和历史；不要求用户清数据或反复授权。

测试/修复/部署：NOT_RUN（针对本故障）。本次仅完成运行诊断与静态定位。不得把合并轮旧测试写成 OOM 修复通过。

## 可复用经验

状态、统计和来源查询应直接读取其需要的字段，而不是调用详情函数再裁剪。数据库压缩尺寸不能用来推断 Go 堆内存。容器当前 OOMKilled=false 不能排除先前重启发生过 OOM，需结合内核、RestartCount、StartedAt 和反向代理时间线。
