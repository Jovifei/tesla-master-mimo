# 2026-10-30 Fleet 原始时间与历史资格问题

## 发现与影响

发现版本：线上 API `ab9a245c`、已安装 App 2.1.58 / build77（代码 `a760b13f`）。Fleet 在放行 4443 后已收到真实车辆数据，但接收成功不等于可证明行程发生时间。

官方 v0.9.4 的车辆 Payload 含 `created_at` 和 `is_resend`，其 MQTT 逐字段格式却只转发字段值；现行 API 以接收时间生成观察时间和事件身份。重连补发或 MQTT 重投可能被视作新观测，甚至生成重复或时间不准的行程。对当前部署源码的隔离回归复现 4 项失败：旧值刷新、重放生成重复行程、旧值覆盖新值、倒序打开行程。账号和车辆隔离等 5 项控制通过。

23:17 的一条原生行程只有接收时刻，不能证明真实驾驶时刻或与归档不重复；它与 5 条已归档行程的严格轨迹/里程比较未找到匹配，但这也不能证明不是同一次行程。原记录保留，不删除、不猜时间。

- 服务端无源时间隔离候选在独立副本中完成离线测试，428 项通过、103 项跳过；未部署。复审发现 Room 旧缓存仍可能显示为合格、原始回执无限增长、旧 open session 和较早可信时间的迁移、独立 summaries 读口等缺口，必须修复并通过真实 PostgreSQL 集成后才可发布。
- 官方 producer 的完整包 MQTT 原型在独立副本中保留源时间、重发标记与字段顺序。复审后已在候选中禁止不兼容的 decoded 配置、拒绝非空车辆身份冲突，并移除 DEBUG 原始负载；合成测试、MQTT/telemetry 回归和 vet 通过。streaming 原生依赖仍未通过本机编译；broker ACK 不代表数据库提交或持久化。原型未部署，不能作为端到端通过证据。
- 后端 envelope 解析候选正在隔离工作树开发，使用官方生成的 protobuf 类型；数据库写入、消费者 ACK、资格迁移和真实事件均未通过端到端验收。
- 后端仅报告未知记录数量不足以让已安装 App 撤销 Room 中具体旧记录的资格。需要按账号、API 来源、车辆、记录身份及原始证据摘要绑定逐条判定，旧服务、离线或没有证明的记录保持未知，不得因列表缺席或来源字符串自行判定。

## 后续修复与验收

1. 保留收到的原始证据；端到端传递并验证车辆源时间、重发标记及稳定事件身份，分别记录接收时间和车辆时间。明确数据保留容量与可靠 ACK 边界。
2. 服务端提供按当前用户、车辆和来源隔离的逐记录时间资格证明；旧记录不能被删除、伪造或按接收时间平移。处理旧 open session、旧 latest 与 summaries 等迁移边界。
3. App 持久化独立资格，保护原始 `apiEvidence` 和用户编辑。列表、详情、统计、停车推导及通知必须在合并/缓存后重新执行资格校验；未知或已撤销不能被旧响应重新提升。
4. 用隔离 PostgreSQL、可重开的真实 Room、重连/乱序/重复消息、跨账号/车辆 ABA 和真实消费者回归验证；再进行生产部署与自然车辆事件验收。不能把首个接收事件或模拟数据当作可信行程完成验收。
