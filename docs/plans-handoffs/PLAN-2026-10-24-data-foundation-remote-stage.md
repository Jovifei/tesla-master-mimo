## 本地已完成的审查和候选

固定 PR #22 源码与官方字段文档交叉核对后，建立 `docs/DATA-FOUNDATION.md` 数据矩阵，并在旧 `DATA-CATALOG.md` 明确原型字段清单不能证明真实上传。官方 Fleet Telemetry 有 `EnergyRemaining`、温度与逐轮 TPMS；MateLink 当前订阅温度和 TPMS，却没有把 `EnergyRemaining` 纳入配置。服务端保存最新字段与完成的会话，Android Room v23 保存摘要、详情、TPMS、费用覆盖；`allowBackup=false`，不能宣称换机恢复所有本机数据。TeslaMate 归档桥只按递增 ID 轮询，旧 ID 更正不会自动进入接收链。

本地候选修改包含：

1. JourVolt 会话刷新的账号代次 CAS；迟到 200/401、旧请求借用新账号令牌的负例；刷新、授权票据交换、Bearer API 拒绝自动重定向。
2. `VehicleStatusStore` 从裸数字车 ID 改为账号／API 来源／车辆本地身份作用域；首页和地图增加迟到响应检查；无 GPS 的快照仍尝试保存其他字段。
3. 旧可信 TeslaMate 行程的真实车内外温度可按原始 receipt、ID 与时间窗进入趋势；冲突、伪造和过期证据继续拒绝。
4. 统计页在已有充电记录但零条费用样本时，把笼统“不可用”解释为“未记录，可在充电详情补录总价”；真实零仍是可用费用。

## 必须集中关闭的复审缺口

当前 WIP 是 CHANGES_REQUIRED，远端需自行读取真实调用链、补 RED→GREEN，不能仅依赖现有纯策略测试：

同一 `c2c_8f2d` 聊天对 PR #22 的已保存复审还指出以下四组 P1；网页答复在连接中断前未完整结束，故请按固定源码再次核实并和本次缺口合并处理，而不是另发四个小任务：

| 旧复审缺口 | 真实反例与需要的消费者验证 |
| --- | --- |
| 同数值 ID、不同来源实例 | 当前 `charges_summary(carId, chargeId)` 主键可使 B 实例的会话覆盖 A 的唯一原始 receipt；要求 A→B→A、多页同步与 Room 重开均可核验旧新来源，不跨源提升能量或费用。Drive 同类路径一并检查。 |
| 合格详情标量但缺点数组 | 一条会话有合格 24.02 kWh，却没有 `charge_details` 数组时，现有详情点准入可能回滚整个摘要事务；列表离线重开又变未知。会话摘要资格与曲线点完整度应独立，点真的损坏或截断则继续严格回滚；前台详情与后台 Sync 都需验证。 |
| 年度 PDF 的混合快照 | 切年份或账号后，PDF ViewModel 可能从旧 `carStats` 和新 `uiState` 拼一份文件；导出应锁定同一账号、来源、车辆、年份、币种与 Room cohort，并核对真实生成的 PDF 内容。 |
| 历史列表迟到发布 | `ChargesViewModel` 在同 numeric carId 换账号/来源时，异步 aggregate 或 car settings 返回可污染新列表；`DrivesViewModel.loadUnits` 也需同响应身份。用 A→B 相同 ID、迟到 DAO/设置与最终 UI 消费者验证。 |

1. `DashboardViewModel` 的 legacy 轮询分支在完成身份检查后调用可挂起的 `loadCachedAddress`，返回后缺最终身份检查；A 账号旧地址仍可能覆盖 B 账号屏幕。
2. 首页当前把“历史车辆 UID 证据尚不可用”当作拒绝整个实时状态的理由。应允许**当前账号、当前车、当前请求**的 live 响应只显示不落缓存；缓存读写仍须有已验证车辆身份。错误状态也不得覆盖新账号 UI。
3. `VehicleStatusStore.reconcileAndSave` 将旧 GPS 与新无 GPS 快照合并，再以新 `observed_at` 保存整个对象：旧位置被伪装成新观测；部分实时响应还可能擦掉先前有效但未在本次返回的其他字段。须把原始实时状态与历史位置/字段证据分开，或选择 fail-closed 的最小方案；离线重开验证数值、位置时间和来源。
4. `/cars` 失败而 `/snapshot/{id}` 成功时，旧数字 ID→UID 映射可把 B 车新状态写进 A 车缓存；地图 `resolveRemote` 的缓存回退亦有同类风险。实时写入需要新鲜、同账号的稳定 UID 证明；无法证明时可展示当前会话的 live 值，但不得归档到旧车辆身份。轮询路径尤其要检查 UID 重绑。
5. `DashboardStatusIdentityTest` 目前测试纯判定函数，不能代替真实 ViewModel 网络迟到/账号切换消费者回归。补真正的 resolver/store/VM 负例，或如实保持未验证门。

上面是独立复审发现的具体反例。不要因为第一轮 20 项 PASS 就忽略它们；也不要通过全局隐藏状态、抹掉旧手机历史或把未知改为 0 来使测试变绿。

## 下一阶段必须由远端自己规划并实际实施

关闭上述 P1 后，远端以当前源码、项目最终目标和官方/开源实现为依据，选择一组**完整且有实际用户价值**的数据功能继续实施，而非只写计划。优先候选：

- 让现有真实温度、胎压、行程和充电字段沿来源→有界服务端历史→Room→列表／详情／趋势／诊断有一致的时间、单位和身份资格；修复确实被错误过滤的值。
- 同一行程的净能量与配对里程使用 `100×Σ合格kWh/Σ同集合km`，保留负回收、真实 0、未知和覆盖；充电总价可单独记账，单价只在同一充电/同币种/合格正能量配对后计算。
- 空态采用具体原因、来源、最后观测时间和一个适用操作；确认无上游记录时诚实显示“未采集／尚无合格历史”，不伪造数字，不用读时充当观测时。已有 443 条有效里程行程、29 条能耗样本、61 条充电能量样本而费用未知的手机页面，不应把一个字段未知说成全部历史为空。
- TeslaMate v4.3.0 新的历史温度呈现和车辆排序可借鉴，但只在 MateLink 真正具备时间序列/账号与稳定 UID 设置时展示。Fleet `EnergyRemaining` 可作为之后新增的标称端点估算候选；若本阶段实施，必须先做字段支持、采样覆盖、来源/时间窗、Server→App 持久证据与旧客户端兼容，并保持“估算”标记。不得凭上游字段名单直接画曲线。

方案要覆盖 Android 与正式长期 Web、小程序的共享数据合同，但本轮产品实施重点是 App 真消费者。若选择改 Go schema、真实历史回填或生产配置，先限定为离线源码／隔离副本资格；运行时写入和生产变更保留单独门。
