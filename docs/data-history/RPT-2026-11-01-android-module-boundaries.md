# 2026-11-01 Android 模块边界审查

## 本轮范围与原则

Jovi 要求每次修改后检查受影响页面，并减少行程、充电、首页和分析功能的交叉副作用。本次在 App 专用 worktree 审查数据获取、身份、计算、缓存和展示；不以大规模改名或迁移代替行为验证，不修改小程序工作区。

## 已识别的耦合

## 本轮落地与验证要求

- 行程能耗：原始提供方证据、可信详情回执、本机估算和 UI 文案分开；完整功率窗口才能显示近似估算。无证据不造值，账号/车辆/来源/记录/窗口改变时拒绝迟到结果。
- 行程地点：同点坐标对与时间窗在服务端验证；App 每端按完整坐标对合并，反查需有上限、可增量发布并防止旧请求覆盖新身份。
- 每次变更分别核查首页、行程列表/详情、充电列表/详情和相关分析页；自动测试使用隔离合成数据，真实手机仅做保数据覆盖安装和实际页面核验。
- 上表列的是已确认或待验证的架构风险，不表示本轮已全部重构或上线。历史问题与版本见 [行程排查记录](RPT-2026-11-01-drive-data-regression.md) 和 [问题账本](..\APP-ISSUE-VERSIONS.md)。

## 行程地点补全并发与性能风险（2026-11-01，源码复核）

以下是源码审查和可由调用路径构造的风险，候选实现及故障测试尚未完成整体验证，尚无真机性能或卡死证据。

1. **行程地址反查的物理调用上限与恢复边界**：高德 `GeocodeSearch.getFromLocation` 是同步调用，协程五秒超时不能强制中断它。当前未发布候选对本进程的**行程自动反查入口**设置两个物理槽；只有底层调用真正返回才释放槽位。满槽时保留释放序号并等待一次释放事件后重试，等待可由页面关闭或身份变化取消。该限制不代表首页、充电等所有高德调用共有两个槽。多等待者同时醒来抢同一个槽时，未抢到者可能退出；已经拿到槽的请求自身超过五秒后也不会自动等待底层调用返回再重试。同一目标超时后若用户再次刷新，最多可能同时存在两个物理调用（包含原请求）；这不是生命周期内调用总次数的上限。上述行为及迟到结果的账号、车辆、来源、回执栅栏均需完成故障测试和真机验证，不能描述为 SDK 调用已被超时中断。
2. **同地点多行程的投影开销**：早期候选对每个命中行程分别扫描列表并重算；当前候选按行程编号分组，合并同一回调的已验证地址后重算一次，仍逐目标查询 Room 并校验身份和回执。40 次限制针对不同坐标，不限制同一坐标命中的记录数；大量历史行程位于同一地点时，查询数量和一次列表重算仍需测量。后续可评估批量读取，但必须继续验证每条记录的身份、来源、坐标、回执和已有地址，不能以降低查询数放松隔离。当前候选尚未完成性能、账号切换和真机回归。

## 行程能耗自动补全请求预算（2026-11-01，候选审查）

早期候选按单个补全任务限制详情请求数量；同一次刷新中的多个任务仍可能累计超过 20 次，失败后也可能由后续任务再次发起。未发布候选已加入同刷新共享预算与错误熔断，并保留账号、车辆、记录与回执校验。最终候选 Debug 定向 5 组共 55 项通过；完整 Debug/Release、lint、模拟器和真机验证仍在进行，不能称为已上线修复。

**失败停止的取舍**：候选逻辑中，同一刷新周期若某条详情返回 503 或请求超时，该周期的预算停止接受后续网络详情请求，包括之后到达的新行程；这样可以控制弱网或服务异常时的请求量。下次前台刷新会创建新预算，可重新处理尚未尝试的记录；已尝试记录的远端重试仍受尝试标记及手动刷新控制，已验证的本地详情应独立读取。此结论来自源码路径，尚待完整回归和真机验证，不能声称 503 期间每条迟到行程都会立即补出能耗。

## 费用链路补充审查（2026-11-01，源码核对）

以下结论来自当前 App worktree 的代码和提交历史，**未在真实用户账号或手机上复现**，也不表示已完成修复。

### Fleet 部分区间估算未进入成本页

- **触发与影响**：`61535c94` 新增对符合合同的 Fleet 部分观测电量的估算，充电列表可以显示 `≈` 费用；成本页调用的 `ChargeCostTotals.calculateCostTotals` 仍先要求完整的 `batteryInputKwh`，因此即使其估价函数可以计算该部分区间，也会被提前跳过。相同记录在两个页面可能出现有估价与无估价的差异。
- **归因边界**：成本汇总原有完整电量门槛不是本次新写的；本次新增的部分观测能力暴露了跨页面缺口。部分观测仅覆盖已采集时间段，不能当成完整充电或正式账单。
- **安全修法**：先分别表示完整记录估算与已采集部分估算及其数量；部分值必须在显示上明确为“已采集部分估算”并使用 `≈`。已记录及手工总价、完整电量和费用/电量配对均价继续依据各自完整证据计算，不将部分值静默混入。复用 `estimateChargeTariff` 按观测时间窗口计算；分时设置无效时不得暗中改用默认价，手工金额和可验证账单仍优先。
- **必要验证**：使用同一合成 Room 数据验证充电列表与成本页的部分估价及标签一致；覆盖完整与部分混合、手工覆盖、已知账单、零值、缺失数据、币种冲突、无效费率、切车及迟到结果。月图、地点图、里程和年度汇总的费用口径要另行明确并验证，不能直接合并估算与已确认金额。

### 自托管旧记录的手工费用来源未绑定

- **触发与影响**：兼容旧自托管数据允许充电记录 `source == null`。`ChargeCostOverrideStore.saveBound` 可将该记录的手工费用保存为 `sourceKind == null`，但 `ChargeCostProjection.manualQualificationReason` 将空来源判为 `legacy_unverified`。因此保存成功后，该金额无法作为已确认手工费用进入正式投影，页面可能仅显示待核实金额。
- **归因边界**：来源资格判断来自较早的 `2815e41f`，并非 `61535c94` 或 `e6a8ea6d` 新引入。当前用户云端记录是否满足这一触发条件尚未验证，不能将此推断成其实际问题的根因。
- **安全修法**：在已验证的自托管账号、车辆、来源和记录时间窗口范围内，为无来源标记的旧记录建立明确的来源凭据，并保持旧金额与新记录的隔离；不能简单放行所有空来源，也不能迁移或删除用户已有金额。
- **必要验证**：使用真实 Room/Store 与 ViewModel 的合成数据，覆盖保存、重新打开、更新及清除手工金额，并验证跨账号、跨车、跨来源、复用数字 ID、时间窗变更、币种变更与并发编辑均不误绑。
