## 目标与本轮边界

目标：真实已结束行程自动进入当前账号、当前车辆的历史；手机打开页面无需绕到仪表盘手动刷新。手机离开家庭 Wi-Fi 后仍可通过云端读取。Fleet 最终接管新增采集，不依赖本地电脑。

本轮只读检查并编写计划；未修改业务代码、部署、安装、提交或推送。保留已有未提交文件、手机登录/历史、TeslaMate 原卷及云端原始证据。后续提交遵守用户指定分支，不提交 main，不直接用当前旧主目录打包覆盖手机。

## 2. 原因判断

当前是多个未闭合环节叠加，而非一个登录按钮能解决：

1. TeslaMate 已写入真实新行程，但本地桥接未运行，不能自动进入云端归档。
2. Fleet 云端仍缺少真实首事件证据；具体断点须沿配置、接收、消息、落库逐段定位。
3. 自托管手机即使有读取能力，也依赖本地主机和网络可达；缓存刷新触发仍需验证。

登录只建立账号会话，不能代替采集就绪、归档授权及页面刷新。历史列表更新与系统通知是两项独立能力，本次先保证数据到达与自动展示，不将通知权限当成历史缺失的原因。

## 3. 执行顺序与检查清单

### P0：恢复准确基线，逐段定位同一条新行程

- [ ] 恢复可用的隔离 checkout，核对 archive/telemetry 分支、远端 SHA 和 build 34 构建记录；找回尚未提交的 Android 修复证据。找不到时明确标记，禁止宣称已恢复。
- [ ] 检查手机当前连接模式、脱敏后的服务端标识、账号/车辆作用域及网络。保留现有模式，不为排障清空或重新登录。
- [ ] 选源库一条最新已结束记录；比较源库 → Adapter API → 云端归档 → 手机列表的来源 ID、UTC 起止时间、点数和更新时间。报告不含 VIN、地址、坐标、token。
- [ ] 真机复现同一页面停留、切页返回、后台恢复、下拉刷新四种情况，确认请求是否发出、API 是否含记录、Room 是否入库、UI 是否更新。

文件：DrivesScreen.kt、DrivesViewModel.kt、DashboardViewModel.kt、DataSyncWorker.kt、SyncRepository.kt、VehicleContextRepository.kt；先定位实际基线再修改。

命令：`git status --short`、`git rev-parse HEAD`、`docker ps`、`adb devices`、脱敏 SQL 与已认证历史 API 对照。证据输出：逐段时间与记录一致性表。

门禁：只有找到首个丢失边界才确定代码改动；P0 不做生产写入。源码基线不明时停止构建安装，不影响现有服务。

### P1：优先交付一条稳定的新行程读取链路

- [ ] 针对已复现的 UI/同步缺陷先加失败测试，再最小修复：页面进入/恢复时按新鲜度拉取、同账号车辆请求去重、远端结果持久化后通知列表。
- [ ] 切换账号、车辆、云端/自托管时取消或丢弃旧请求，避免晚到响应串数据。
- [ ] 同步状态显示数据源、最后成功获取时间、最新记录时间、明确失败阶段；缓存不能显示为刚同步成功。
- [ ] 断网继续显示原记录并提示过期，不将错误变成空列表或零值；重连补拉，不要求杀 App。

验证：在正确 Android checkout 执行 `./gradlew.bat :app:testDebugUnitTest :app:lintRelease`；新增同车恢复、并发刷新、切源晚响应、离线重连测试。同签名覆盖安装前核验证书、APK SHA、版本、首装时间。

验收：服务端已有新记录后，前台进入/恢复历史页在正常网络下 30 秒内可见，不需先点仪表盘；这是验收目标，不是后台时效保证。真实设备单独记录结果。

回退：停用新调度，保留原缓存及手动刷新；不卸载、不降级清数据。

### P2-A：完成个人 TeslaMate → 云端 → 手机（与 P2-B 并行）

- [ ] App 提供来源绑定确认/取消/撤销入口；核验稳定车辆身份，不按数字 carId、车型或昵称认领。
- [ ] 定义安全 enrollment：短时一次性配对、来源设备确认、受保护传输与凭据存储。用户不填 .env、不传密码/token 给聊天。
- [ ] 澄清旧计划：创建/撤销绑定使用用户会话；无人值守桥接使用仅限归档上传的可撤销来源凭据，不持有普通用户会话。不能把 hash 当上传凭据发送。
- [ ] 数据库强制只读角色，不回退使用 TeslaMate owner；归档 HTTPS 和重定向边界受控。
- [ ] 服务端完整确认落库后推进作用域绑定的断点；不能只看 HTTP 2xx。补分块原子发布、迟到完成、旧记录修正、每日核对。
- [ ] 隔离 PostgreSQL 验证迁移、旧记录 nullable 字段读取、幂等更新、撤销及双账号隔离，不拿内存测试代替数据库测试。
- [ ] 一条真实行程、一条真实充电小批验证后，开启全量及持续上传；源与云校验记录、日期及采样，不静默截断。
- [ ] 手机切云模式后在蜂窝网络核验同一归档，不依赖直连家庭 LAN。

文件：deploy/jourvolt-dev-mock 下 archive_binding.go、telemetry_import.go、telemetry_store.go 与实际路由；deploy/teslamate-home-docker/archive-bridge；Compose；Android readiness/API/repository。

验证：在两个 Go 模块分别 `go test ./... -count=1`、`go vet ./...`；独立 PostgreSQL fixture 覆盖重复、断网、重启、撤销、修正、跨租户拒绝。完整长期归档、来源证据保留，不将归档成功算 Fleet 成功。

验收目标：本地结束记录发布后，桥接每分钟检查，正常联网时 3 分钟内可从云 API 读取；App 再按 P1 刷新门禁验收。主机离线必须提示，不能承诺停机期间采集。

回退：停止 bridge 或撤销其凭据；不删除源库与已归档记录。生产迁移前备份并验证恢复，容量不足停止扩批。

### P2-B：修复多用户 Fleet 主链路，不等归档全部完成

- [ ] 对当前车辆核验区域、官方权限、虚拟钥匙状态、签名配置请求及配置读取确认。
- [ ] 核验接收端 TLS/CA、实际入包、MQTT 消费、车辆路由及会话落库；记录首次中断环节。
- [ ] 诊断仅保存关联 ID、阶段、HTTP 状态、稳定错误类别和时间，不保存令牌、VIN、位置、上游原始正文。
- [ ] 只在官方返回缺权限/钥匙等明确原因时，App 引导用户去 Tesla 官方确认。已有有效授权不重复要求登录。
- [ ] 对定位到的最小缺陷加失败测试；配置重试幂等、并发互斥，真实回读成功才标记 config_synced。
- [ ] 证明真实车端事件 → 接收 → 消费 → 行程结束落库 → 云 API → 手机完整经过；排除归档和模拟事件。

文件：实际基线中的 Fleet provider、Telemetry 配置/接收/store/http、Command Proxy/receiver Compose 配置、Android readiness 状态呈现。准确文件路径由 P0 的符号检索确认，不臆造缺失文件。

验证：定向 Go 回归与隔离 PG；生产只读诊断先行，后续部署按不可变 SHA/构建清单执行，保留旧镜像及配置。失败回退 API/配置，不清消息或原始数据。

### P3：用户验收与正式接管

- [ ] 两账号、多车辆交叉读写与错误绑定均被拒绝；不同来源重叠不重复统计。
- [ ] 前台/后台恢复、Wi-Fi/蜂窝、断网重连、设备重启均验证；后台受系统调度影响，不承诺即时推送。
- [ ] 至少 7 天、3 趟真实行程、1 次真实充电并行核对；Fleet 稳定后才停 TeslaMate 主动采集。
- [ ] 提交验收包：源码 SHA、构建/安装 SHA、测试报告、逐层脱敏证据、失败项与回退说明。

完成判据：手机持续获得真实新记录，云端完整可恢复，多用户隔离，Fleet 接管后本地电脑关闭不影响新增采集。以上全部通过前不得标记项目完成。

## 4. Jovi 与开发方各自要做什么

开发方负责定位、代码、配置、桥接安全接入、部署和测试，不再把内部 .env 配置交给普通用户。Jovi 只需在确有必要时于 App/Tesla 官方页面确认车辆/权限，正常驾车充电，最后核对展示结果；不提供账号密码或令牌。
